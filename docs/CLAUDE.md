# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

**Łowcy Historii** (repo name: sight-hunter) is a BEST Hacks 2026 hackathon project: a location-based game where players in Wrocław get a riddle or an archival photo of a place, go there, photograph it, and receive points/XP and an unlocked short video ("reel") about the place's history.

State: `api/` implements the whole contract except the daily mini-game (see `api/README.md` → Status); `mobile/` is an Expo skeleton with create-expo-app demo screens; `docker/` + `docker-compose.yml` run Postgres, Redis, SeaweedFS, api and api-worker; `worker/` and `content/` only have READMEs. The design source of truth is in `docs/`: `Łowcy Historii — архитектура и стек.md` (architecture, data model, endpoint flows), `Łowcy Historii — план работ на 4 человек.md` (work plan, scope cut order), `Łowcy Historii — opis projektu (BEST Hacks 2026).md`, and the HTML UI prototype `Łowcy Historii.html`. Read the relevant document before implementing a feature. Real build, lint and test commands are in each folder's README (`api/README.md`, `mobile/README.md`, `mobile/AGENTS.md`).

## Planned layout and stack

Monorepo:
- `api/` — FastAPI + Pydantic v2, SQLAlchemy 2 (async) + Alembic, SQLAdmin for content. Modular monolith with modules `auth`, `quests`, `finds`, `wallet/XP`, `media`, `social`, `shop`, `admin`; each module has `models / schemas / repository (queries) / service (rules, transactions) / router`. Routers call services only; modules talk to each other through services. Boundaries stay clean so `recognition` and then `media` could later be split out as services.
- `worker/` — separate Python process (arq on Redis) for photo recognition: OpenCLIP/DINOv2 embeddings, cosine similarity against reference photos in pgvector (HNSW), LLM vision judge only for the gray zone between two thresholds.
- `mobile/` — Expo + TypeScript, expo-router, TanStack Query, Zustand, expo-camera, expo-location, expo-video, react-native-maps, tokens in expo-secure-store. TS API client generated from OpenAPI (orval or openapi-typescript), not hand-written.
- `content/` — scripts such as `fetch_places.py` (OSM Overpass / Wikidata / Commons), `add_refs` (reference embeddings), `generate_reel.py` (facts → script → TTS → ffmpeg 720p vertical with subtitles and a sources card).

Infra: PostgreSQL with PostGIS + pgvector (custom image from `postgres:17` plus both packages — no official image has both), Redis, S3-compatible storage (SeaweedFS locally — MinIO images are no longer published; Cloudflare R2 in prod). Local dev is `docker compose up` (api, api-worker, postgres, redis, seaweedfs).

## Core architecture rules

- **Async photo verification flow:** `POST /rounds/{id}/attempts` (server-side PostGIS `ST_DWithin` geofence check *before* upload, `too_far` with distance) → presigned PUT straight to storage (files never go through the API) → `POST /attempts/{id}/submit` (idempotent, enqueues `verify_attempt`, returns 202) → worker writes verdict → client polls `GET /attempts/{id}` ~1/s.
- **Money is a ledger:** points (`wallet_ledger`) and XP (`xp_ledger`) are append-only; balances are computed from them, never stored as a mutable number. XP is leaderboard-only; points are shop currency.
- **Reward is one DB transaction:** `finds` (unique `user_id, task_id`) + both ledger entries + `reel_unlocks` + round closed. Redis leaderboard `ZINCRBY` happens after commit; leaderboard must be rebuildable from `xp_ledger`.
- Hints (max 3 per round) never touch the player's balance and there is no hint stock (team decision 2026-10-10, overriding the prototype): each hint cuts only the round's **points** by 25% of base, floored at 25%; XP is unchanged. The shop therefore sells public reels only.
- Rewards are paid by the backend, not the ML worker: the worker returns a verdict via the `apply_verdict` arq job (queue `arq:queue:api`); `api/app/worker.py` does the reward transaction. Contract in `api/README.md`.
- Purchases lock the user row (`SELECT … FOR UPDATE`) before checking balance; hints/submit/purchase accept an `Idempotency-Key`.
- The server decides everything that changes points, XP or content access; the client only displays results. Unfound places are shown as an offset zone, not the exact point. Hint texts and correct answers are never sent before they're earned.
- API is under `/api/v1`, JWT access (~15 min) + refresh. Error codes are part of the contract: `too_far`, `wrong_place`, `insufficient_points`, `email_taken`, `invalid_credentials`, `nickname_taken`.
- Reels store `video_provider` + `playback_url`, not hard-coded paths.
- Privacy (NFT-06): player photo is deleted from storage after the verdict; coordinates aren't kept after the round.
- A server "demo mode" flag accepts a manually set position (long-tap on map) — never remove it.

## Team conventions

- All user-facing text (UI, tasks, hints, reel subtitles/voice-over) is in **Polish**.
- The OpenAPI contract changes only by team agreement and is updated immediately; mobile works against mocks until an endpoint is ready.
- `main` must always run; work in branches and merge via PR.
- Secrets live in `.env` / `.env.local` (both gitignored), never in git.
- Scope cut order if short on time (first to cut first): daily mini-game/partners → password reset → comments/share → shop beyond hints → LLM judge → Redis leaderboard → number of places. Never cut: full round loop, demo mode, the sources card in reels.
